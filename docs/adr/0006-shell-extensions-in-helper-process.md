# 0006. 셸 확장은 도우미 프로세스에서만 로드한다

- 상태: 채택
- 날짜: 2026-11-15

## 맥락

오른쪽 메뉴, 썸네일, 미리보기에서 탐색기와 같은 항목을 보이려면 설치된 다른 프로그램의 셸 확장을 불러야 한다. 이들은 남의 DLL이라 느리거나 죽는다. facet 프로세스 안에 로드하면 확장 하나가 죽을 때 모든 창과 진행 중인 파일 작업이 같이 죽는다.

## 결정

- 셸 확장은 전부 도우미 프로세스에서 로드한다. 도우미가 죽으면 도우미만 다시 띄운다.
- 오른쪽 메뉴는 facet 자체 항목을 즉시 띄우고, 셸 확장 항목은 도착하는 대로 아래에 붙인다.
- 썸네일은 흔한 이미지 형식을 자체 디코더로 그리고, 나머지만 도우미에 맡긴다.

## 예외 (2026-11-15)

아래 두 가지는 UI 프로세스에서 셸을 부른다. 도우미를 거치지 않는다.

- **휴지통으로 삭제와 복원**(ADR-0005, S4). 셸의 파일 작업 인터페이스가 다른 프로그램의 복사 훅을 UI 프로세스에 실을 수 있다.
- **가상 폴더용 셸 공급자**(ADR-0004, S12). 내 PC, 휴지통, 연결된 휴대폰의 셸 폴더는 Windows가 넣은 구현이라고 본다.

이유: 도우미를 거치면 S4가 S9를 기다려야 해서 탐색기 대신 쓸 수 있는 시점이 늦어지고, 프로세스 너머로 목록을 나르는 비용이 든다. 대신 두 호출 모두 전용 STA 스레드에서 하고 시간 제한을 둔다. UI 스레드에서는 부르지 않는다.

남는 위험: 이 두 경로에서 실린 남의 DLL이 죽으면 facet도 죽는다. 그런 일이 실제로 보고되면 해당 호출을 도우미로 옮긴다.

오른쪽 메뉴의 셸 항목, 썸네일 공급자, 미리보기 처리기는 예외가 아니다. 계속 도우미에서만 싣는다.

## 아이콘 (2026-11-18, #325)

파일 종류별 아이콘(자세히 보기, 뒤의 그리드 보기)은 안전 래퍼(`facet_win::icon`)가 셸의 시스템 아이콘 목록(`SHGetFileInfoW`·`SHGetImageList`)에서 얻는다. UI 스레드가 아니라 코어 아이콘 캐시의 일꾼 스레드 하나에서 부르고, 확장자마다(크기마다) 한 번만 얻는다. `.exe`·`.ico`·`.lnk`·`.url`만 파일마다 얻는다(온라인 전용이면 내려받기를 막으려고 확장자 아이콘).

아이콘 처리기 확장(`shellex\IconHandler`, 제3자 DLL)을 싣는지 확인한 결과:

- **확장자·폴더 아이콘**(`SHGFI_USEFILEATTRIBUTES`, 파일을 열지 않음): 제3자 아이콘 처리기가 없는 CI 러너(Windows Server 2025)에서 확장자 18종과 폴더 아이콘을 얻은 뒤 새로 실린 DLL은 모두 `C:\Windows` 아래 것이었다(`windows.storage`·`comctl32`·`windowscodecs`·`propsys` 등).
- **파일마다 다른 아이콘**(실제 경로): 같은 러너에서 시스템 실행 파일 3개와 시작 메뉴 바로 가기 172개를 얻은 뒤에도 새 DLL은 모두 `C:\Windows` 아래 것이었다(`linkinfo`·`iconcodecservice`·`urlmon` 등). 그러나 이 경로는 셸이 항목의 `IExtractIcon`을 만들고, 바로 가기는 아이콘 위치가 없으면 대상 항목의 아이콘을 얻으므로, 대상 형식에 제3자 아이콘 처리기가 등록된 기계에서는 그 DLL이 facet 프로세스에 **실릴 수 있다**고 본다.

그래서 파일마다 다른 아이콘 경로를 도우미로 옮기는 후속 이슈(#363)를 열었다. 옮기기 전까지는 이 경로가 UI 프로세스에서 남의 DLL을 실을 수 있는 남는 위험이다(휴지통·가상 폴더 예외와 같이 UI 스레드 밖의 전용 스레드에서만 부른다). 제3자 처리기가 있는 기계에서의 확인은 사람이 한다(Process Explorer로 facet 프로세스의 DLL 목록).

## 미리보기 처리기 창 붙이기 (2026-11-18, #343)

셸 미리보기 처리기(`IPreviewHandler`)는 도우미가 미리보기 전용 COM STA 스레드에서 싣는다(`facet_win::preview_handler`, 도우미만 부름). 처리기 창을 facet에 보이는 방식으로 spec #26이 둔 두 갈래 가운데 **창 붙이기**를 골랐다:

- 도우미가 그릇 창(`WS_CHILD`)을 **facet 창의 자식 창으로** 미리보기 영역 자리에 만들고, 처리기는 그 안에 `SetWindow`로 그린다. 자리는 facet이 화면 물리 픽셀로 알리고(`PreviewHost`), 도우미는 그 스레드를 Per-Monitor v2 DPI 문맥으로 두어 facet 창 안쪽 좌표로 바꾼다. 영역이 옮겨지거나 크기가 바뀌면 그릇 창을 옮기고 `SetRect`한다.
- 다른 항목·영역 끄기는 `Unload` 뒤 그릇 창을 없앤다. 도우미가 죽으면 그 프로세스의 창은 운영체제가 없애므로 붙인 창도 사라지고, facet은 「미리보기를 불러오지 못함」을 보인다.
- **포커스**: 붙인 창이 키보드 포커스를 가져가면(처리기가 스스로 가져가거나 사용자가 눌러서) facet 창이 포커스를 잃는 순간 이벤트를 다 처리한 뒤 facet 창으로 되찾는다(`facet_win::reclaim_focus_from_child`, facet이 활성 창일 때만). 그래서 목록 키보드 이동이 늘 이어지고, 미리보기 안에서 키보드로 움직이는 것은 하지 않는다(spec #26의 「포커스는 목록에 남는다」). 마우스(누르기·휠)는 처리기 창이 그대로 받는다.

까닭: 탐색기도 같은 방식이다(처리기를 대리 프로세스 `prevhost.exe`에서 싣고 그 창을 탐색기 창에 붙인다). 처리기는 창에 직접 그리도록 만들어져 있어(영상 재생, PDF 넘기기) 그림으로 보내는 방식은 움직이는 내용을 따라가지 못하고 매번 비트맵을 프로세스 너머로 나르는 비용이 든다. 우려했던 두 문제는 이렇게 막았다: DPI는 facet(winit, Per-Monitor v2)과 도우미의 미리보기 스레드를 같은 문맥으로 두어 물리 픽셀 하나로 맞추고, 포커스는 위처럼 되찾는다. 이 러너(Windows Server 2025)에서 기본 처리기를 숨은 창에 붙이고 옮기고 내리는 것은 시험(`facet-win/tests/preview_handler.rs`)으로 확인했고, 실제 PDF·docx·mp4와 배율이 다른 모니터는 사람이 확인한다(`docs/preview-checklist.md`).

남는 위험: 프로세스를 넘어 부모·자식이 된 창은 입력 큐를 함께 쓰므로, 처리기가 메시지를 처리하지 않고 멈추면 facet 창의 입력도 잠깐 굳을 수 있다. 미리보기 요청은 3초, 자리 바꾸기·내리기는 1.5초 안에 끝나지 않으면 도우미를 끝내(관리 쪽 시간 초과, 도우미 스스로 끝냄) 붙인 창을 거둔다. 또 facet이 미리보기 영역 위에 겹쳐 그리는 것(오른쪽 메뉴·팔레트 등)은 붙인 창 아래에 가려진다. 실제로 문제가 보고되면 그림으로 보내는 방식으로 물러선다.

## 검토한 대안

- **프로세스 안에 로드**: 구현이 단순하지만 느린 확장 하나가 메뉴 전체를 늦추고, 죽으면 앱이 죽는다.
- **셸 확장을 부르지 않음**: 가장 빠르고 안정적이지만 「7-Zip으로 압축」 같은 항목이 없어 탐색기를 대체하지 못한다.

## 결과

- 프로세스가 셋이 된다: UI, 인덱서 서비스(ADR-0003), 셸 확장 도우미.
- 메뉴와 미리보기 창을 프로세스 너머로 붙이는 구현이 까다롭다.
- 오른쪽 메뉴의 항목이 뜬 뒤에 늘어난다. 자체 항목의 위치는 고정해 손이 헛나가지 않게 한다.
