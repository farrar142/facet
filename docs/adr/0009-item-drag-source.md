# 0009. facet 항목 끌기는 OLE 끌기 루프 하나로 하고, 창 이벤트 처리 밖에서 돈다

- 상태: 채택
- 날짜: 2026-11-16

## 맥락

spec #20(S5)의 #185는 facet 항목을 끌어 facet 안(반대편 패널, 폴더 행)과 다른 앱(탐색기·바탕 화면·메일 앱)에 놓는다.
facet 안의 끌기도 다른 앱과 같은 길로 처리해 결과가 같아야 하고, 끄는 동안 커서 옆에 「〈폴더〉로 이동/복사」를
보여야 하며, 오른쪽 버튼으로 끌어 놓으면 「여기에 복사」「여기로 이동」「취소」 메뉴를 띄운다. ADR-0008은 바깥으로 끄는
동안 facet 창이 다시 그려지는지를 이 티켓에 넘겼다.

## 결정

- **끌기 원본은 `facet_win::drag_source` 하나다.** 셸의 빈 데이터 개체(`SHCreateDataObject`)에 파일 목록을 클립보드와
  같은 `CF_HDROP` 바이트로 넣고(`DragObject`), 허용 효과(복사·이동)는 `DoDragDrop`에 넘긴다. facet 창 위에 놓으면 그
  창의 OLE 드롭 대상(ADR-0008)이 다른 앱에서 온 끌기와 똑같이 받는다. 결정은 코어 `dragdrop::decide` 하나다.
  - `Preferred DropEffect`는 넣지 않는다. 붙여넣기용 힌트인데 탐색기가 끌기에서도 기본 효과로 읽어 같은 볼륨 이동이
    다른 효과로 바뀔 수 있다.
  - 셸 항목 목록(`Shell IDList Array`)은 넣지 않는다. 탐색기·바탕 화면·메일 앱(Outlook 등)은 `CF_HDROP`을 받고, 항목
    목록을 만들려면 셸에 경로를 해석하게 해야 해(260자 넘는 경로는 실패) 끌기를 시작할 때 셸을 기다린다. 받지 않는
    앱이 확인되면 그때 더한다(사람 확인 목록).
- **끌기 루프는 창 이벤트 처리 밖에서 돈다.** winit은 자기 이벤트 처리기 안에서 들어온 창 메시지를 처리가 끝날 때까지
  쌓아 둔다. 처리기(Slint 콜백, winit 이벤트 훅) 안에서 곧바로 `DoDragDrop`을 돌면 끄는 동안 facet 창의 다시 그리기
  요청도 쌓여, facet 안에서 끌 때 놓일 폴더 행 강조가 움직이지 않는다. 그래서 문턱을 넘으면 끌기를 스레드 타이머
  (`SetTimer`, 창 없음)로 미루고(`drag_source::run_soon`), winit의 메시지 루프가 `DispatchMessage`로 타이머 함수를 부를 때
  (처리기 밖) `DoDragDrop`을 돈다. 그 안에서 OLE 모달 루프가 펌프하는 창 메시지는 winit이 곧바로 처리하므로 Slint가
  다시 그린다. 끄는 동안 코어를 빌려 둔 곳은 없다(파일 목록은 미리 복사한 경로).
  - 이것은 winit 0.30의 Windows 구현에 기댄 판단이고 자동 테스트가 보지 못한다. 사람 확인 목록
    (`docs/dragdrop-checklist.md`)의 「facet 창 다시 그리기」 항목으로 확인한다. 다시 그려지지 않으면 강조만 멈추고
    놓기와 커서 효과·설명은 그대로다(설명은 셸의 끌기 그림 창이 그린다).
- **끄는 동안의 설명은 셸의 드롭 설명(`DROPDESCRIPTION`)이다.** 원본은 셸의 끌기 그림 도우미(`IDragSourceHelper2`)로
  기본 끌기 그림을 만들고 설명 글자를 허용한다(`DSH_ALLOWDROPDESCRIPTIONTEXT`, 창 핸들은 넘기지 않아 winit 창에
  `DI_GETDRAGIMAGE`를 보내지 않는다). 드롭 대상은 처리기가 준 설명(`DropHandler::label`)을 데이터 개체에 적고 떠나거나
  놓으면 지운다. 그림과 설명은 셸이 이 스레드에 만든 창이 그리므로 facet 창이 다시 그려지는지와 상관없고, 탐색기에서
  facet으로 끌 때도 같은 글자가 보인다. 글자는 앱의 `text::drop_label`이 준다(「사진으로 이동」처럼 받침에 맞는 조사,
  한글이 아니면 「(으)로」, 놓을 수 없으면 까닭).
- **최적화하지 않은 이동이 돌아와도 원본을 지우지 않는다.** facet의 드롭 대상과 탐색기는 이동을 직접 하고 `NONE`을
  돌려준다(최적화된 이동). 다른 앱이 `MOVE`를 돌려줘도(받은 쪽은 복사만 했고 원본을 지우라는 뜻) facet은 받은 쪽이
  다 썼는지 확인할 수 없고, 남은 원본은 사람이 지울 수 있지만 잘못 지운 원본은 되돌릴 수 없다.
- **끌기가 끝나면 그 창에 버튼 놓기 메시지를 보낸다.** `DoDragDrop`이 마우스를 붙잡고 버튼 놓기를 먹어 winit이 버튼이
  눌린 채라고 알고 마우스 붙잡기를 풀지 않기 때문이다.
- **항목 위 누르기와 빈 곳 누르기를 가른다.** 아이콘·이름 글자 위에서 시작한 끌기만 항목 끌기이고 그 밖(이름 칸 여백,
  다른 칸, 목록 아래)은 사각형 선택 그대로다. 이미 선택된 항목을 Shift 없이 누르면 탐색기처럼 고르기를 놓을 때로
  미뤄 여럿을 골라 둔 채 끌 수 있다. 끄는 항목은 선택(누른 항목이 선택에 없으면 그 항목 하나)이다.
- **오른쪽 버튼**: 항목 위를 누르면 선택만 정하고 오른쪽 메뉴는 끌지 않고 놓을 때 연다(탐색기와 같다). 문턱을 넘으면
  오른쪽 끌기다. 오른쪽 끌기로 놓으면(facet 안이든 다른 앱에서 왔든) 드롭 대상이 파일 목록과 놓을 폴더를 복사해 두고
  원본 앱에 「아무 일도 없음」(`NONE`)을 돌려준 뒤, 이벤트 루프로 돌아가 놓은 자리에 고르기 메뉴를 연다(오른쪽 메뉴와
  같은 화면 요소). 원본 앱을 메뉴가 닫힐 때까지 붙잡지 않으려는 것이다. 고르면 facet이 직접 복사·이동하므로(왼쪽 끌기와
  같은 `App::start_drop`) 원본 앱이 할 일은 없다. 메뉴의 꺼진 줄은 코어 결정이 허용하지 않은 효과다.

## 결과

- facet 안의 끌기와 다른 앱 사이의 끌기는 결정·작업·실행취소가 같다. 데이터 개체 만들기와 드롭 대상이 그 개체를
  읽는 길은 Windows 전용 테스트(`crates/facet-win/tests/drag_source.rs`, `crates/facet-core/tests/dragdrop.rs`)가
  확인하고, 실제 마우스 끌기·다른 앱·다시 그리기는 사람 확인 목록이 본다.
- ADR-0008의 「오른쪽 버튼으로 끌어 놓기는 놓을 수 없음」은 이 결정으로 바뀐다.
